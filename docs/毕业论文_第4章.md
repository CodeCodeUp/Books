# 基于协同过滤与内容特征的图书馆资源智能化推荐系统的设计与实现

---

## 第4章 系统实现

### 4.1 开发环境与工程结构

#### 4.1.1 技术栈与运行环境

本系统采用前后端分离与独立算法服务相结合的实现方式，由 Vue 3 前端、Spring Boot 后端和 Flask 算法服务三部分组成。前端使用 Vue 3、Vue Router、Pinia、Element Plus 和 Axios 构建页面与交互逻辑，构建工具为 Vite。后端使用 Java 17、Spring Boot 3.1.5、Spring Security、JWT 和 MyBatis Plus 完成认证、业务接口与数据库访问。算法服务使用 Flask、pandas、NumPy、scikit-learn 和 SciPy 实现协同过滤、内容推荐与混合推荐逻辑，底层数据存储为 MySQL。

从运行形态看，前端默认作为浏览器访问入口，后端通过 `/api` 暴露业务接口，算法服务提供推荐相关的独立 REST 接口。三者在开发阶段通常分别运行在 3000、8080 和 5000 端口，由后端负责承接业务请求并在需要时调用算法服务。

#### 4.1.2 工程目录与关键配置

当前仓库按照职责拆分为三个独立子项目。前端项目位于 `book-recommendation-frontend`，主要包含 `router`、`stores`、`api`、`views` 和 `components` 等目录；后端项目位于 `book-recommendation-backend`，按 `controller`、`service`、`mapper`、`entity`、`config` 和 `common` 分层组织；算法服务位于 `recommendation-algorithm-service`，由 `app.py` 负责接口入口，`algorithms` 负责核心推荐逻辑，`data` 负责数据加载，`utils` 负责缓存和评估工具。

系统的关键配置集中在三个文件中。后端的 `application.yml` 配置了数据库连接、服务端口、`/api` 上下文路径、JWT 参数以及算法服务地址；前端的 `src/utils/request.js` 将所有请求统一指向 `/api`，并在请求头中附带 JWT；算法服务的 `config.py` 配置数据库连接、默认推荐数量以及缓存有效期。除此之外，后端 `WebConfig` 仅对本地开发常用的 `http://localhost:3000` 和 `http://localhost:5173` 开放跨域访问，因此本章实现部分以本地联调环境为主要说明对象。

### 4.2 数据处理与数据加载实现

#### 4.2.1 原始数据获取与基础清洗

系统使用 Book-Crossing 数据集作为初始数据来源。仓库中的 `scripts/download_book_crossing.py` 提供了可复核的数据下载脚本，它会尝试多个镜像地址获取压缩包，并将解压结果保存到 `data/book_crossing` 目录。这样做的目的不是追求复杂的数据采集流程，而是保证论文中所描述的数据来源和项目实际使用的数据目录保持一致。

基础清洗由 `scripts/basic_data_cleaning.py` 完成。对于评分数据，脚本只保留大于 0 的显式评分，并将原始 10 分制评分除以 2 后裁剪到 1 至 5 分范围，以便与系统当前的 5 分评分界面保持一致。对于图书数据，脚本会统一字段命名，修正年份字段的数值类型，补齐标题、作者和出版社中的缺失值，并将结果分别写入 `processed_data/ratings_cleaned.csv` 与 `processed_data/books_metadata.csv`。因此，系统后续使用的数据并不是原始 CSV 的直接副本，而是经过基础规范化后的训练与导入数据。

#### 4.2.2 用户元数据处理与入库脚本

用户侧原始数据的补充清理由 `scripts/process_users_data.py` 完成。该脚本将原始用户文件中的年龄转换为数值类型，将明显异常的年龄设为缺失值，再依据位置字符串提取国家信息，并按年龄生成 `Under 18`、`18-24`、`25-34` 等年龄组字段。考虑到推荐算法的主要输入来自评分行为，脚本还会将用户数据限制为“至少出现在评分数据中的活跃用户”，最后生成 `processed_data/users_metadata.csv`。

需要强调的是，当前仓库中能够直接核实的最终导入主链路由 `scripts/final_import.py` 提供。该脚本主要负责将清洗后的图书与评分导入 MySQL，并在导入完成后统一回填图书表中的 `avg_rating` 与 `rating_count` 字段，再对 CSV 文件和数据库中的计数结果进行校验。换言之，用户元数据清洗脚本已经存在，但当前可直接复核的最终导入脚本并没有把“用户表全量导入”写成与图书、评分完全相同的导入步骤。因此，本章只把仓库中能够由代码直接证实的图书与评分导入链路写入“已实现”部分。

#### 4.2.3 算法服务的数据加载机制

算法服务没有在每次请求时重新全量读取数据库，而是通过 `data_loader.py` 维护共享数据副本。系统启动时，`DataLoader` 会一次性加载评分表和图书表，其中图书数据当前只加载 `rating_count > 0` 的记录，用于减少后续相似度计算的候选规模。首次加载完成后，评分数据与图书数据都会记录各自的最后更新时间。

当用户提交新评分或算法服务需要刷新缓存时，`DataLoader` 会根据 `created_at` 字段执行增量更新。评分数据会将最新评分合并进内存 DataFrame，并按“同一用户对同一图书只保留最新记录”的规则去重；图书数据则更新对应图书的统计字段。这种实现方式兼顾了数据实时性与算法响应速度，是后续预计算和缓存刷新的基础。

### 4.3 推荐算法实现

#### 4.3.1 数据加载模块实现

推荐算法各模块共享同一套数据加载器。用户协同过滤、物品协同过滤、内容推荐和混合推荐都依赖 `DataLoader` 提供的评分数据与图书数据，这样可以避免多个算法模块各自重复读取数据库。对系统实现而言，这种共享方式比完全独立的数据副本更符合当前项目的规模，也方便在评分发生变化后进行统一刷新。

除基础表数据外，数据加载器还提供了获取用户兴趣主题、按主题查询图书等辅助方法。这些方法主要服务于混合推荐中的兴趣加权和冷启动推荐，不直接暴露给前端，而是作为算法服务内部的共享能力被调用。

#### 4.3.2 用户协同过滤算法实现

用户协同过滤的核心逻辑位于 `algorithms/collaborative_filtering.py`。实现时，系统首先读取目标用户的评分历史，收集其已评分图书集合，再从评分表中筛出与这些图书存在交集的其他用户。为了控制计算量，当前实现只对“至少有 2 本共同评分图书”的候选用户继续计算相似度，并使用余弦相似度衡量评分向量之间的一致性。

在得到相似用户列表后，系统按相似度从高到低排序，并截取前若干名作为邻居用户集合。随后，算法从这些邻居用户已评分而目标用户尚未评分的图书中生成候选项，并结合预测评分、图书元数据和最低评分阈值构建推荐结果。由于推荐结果最终还要进入混合推荐模块，因此用户协同过滤在当前实现中更像是一个候选生成器和相似用户发现器，而不是单独暴露给前端的最终推荐逻辑。

#### 4.3.3 物品协同过滤算法实现

物品协同过滤的核心逻辑位于 `algorithms/item_based_cf.py`，主要用于图书详情页的“相似图书”能力。系统首先获取对目标图书有过评分的用户，再从这些用户评价过的其他图书中筛选候选图书。对于每本候选图书，系统统计与目标图书的共同评分用户数，并在共同用户数不少于 2 的前提下计算两本图书评分向量的余弦相似度。

与用户协同过滤相比，物品协同过滤更强调“图书之间的共现关系”。当前实现会将相似度与共同用户数量共同作为排序依据，并在结果中补齐标题、作者、出版社、平均评分、评分人数和相似度说明等字段。这一实现直接服务于详情页的相似图书推荐，也是后续物品侧动态混合的输入之一。

#### 4.3.4 基于内容的推荐算法实现

内容推荐模块位于 `algorithms/content_based.py`。对于有评分历史的用户，系统使用图书的 `title + author + publisher` 组合文本构建 TF-IDF 特征，并额外拼接标准化后的出版年份和平均评分作为数值特征。当前实现中 TF-IDF 向量的 `max_features` 为 1000，而不是旧文档中曾经出现的 1500 或 1502。用户画像通过“用户已评分图书向量的加权平均”构建，其中评分越高的图书对画像的影响越大。

对于无评分历史的用户，系统不会强行构造伪画像，而是进入基于用户基础特征的冷启动路径。该路径优先根据兴趣主题推荐相关图书；若兴趣推荐不足，则继续使用年龄分组补充候选；若仍然不足，则退回到高质量热门图书兜底。对于图书详情页的内容相似推荐，系统优先计算目标图书与候选图书之间的 TF-IDF 相似度；若目标图书缺少可直接使用的内容向量，则退回到作者、主题、出版社、年份和评分差异构成的属性匹配方法。

#### 4.3.5 混合推荐与缓存实现

混合推荐模块位于 `algorithms/hybrid.py`，负责将用户协同过滤、物品协同过滤与内容推荐整合为最终输出。在推荐页中，系统首先判断用户是否具有评分历史、年龄和兴趣信息。若用户既有评分历史又有兴趣主题，则走三层混合路径，在动态混合后继续执行兴趣加权；若用户只有评分历史，则走不带兴趣加权的动态混合路径；若用户无评分但具备年龄或兴趣特征，则直接进入冷启动推荐；若评分和特征都缺失，则降级为高质量热门图书推荐。这里的“动态混合”并不是固定 7:3，而是根据相似用户数量与平均相似度动态计算协同过滤占比。

在图书详情页中，系统会同时尝试生成物品协同过滤结果和内容相似结果。只有当两路结果都存在时，才根据目标图书评分数量、物品协同过滤候选数量和平均相似度动态计算混合比例；若仅有一路结果，则退化为纯物品协同过滤或纯内容推荐；若两路结果都不可用，则算法服务内部先降级为同作者图书推荐。

缓存机制分为两类。第一类是用户推荐文件缓存，由 `utils/cache.py` 负责管理，缓存文件路径包含 `user_id` 和 `min_rating` 参数，算法服务会一次性为用户生成较完整的推荐列表并写入 JSON 文件，然后按照 `offset` 分页返回。第二类是图书详情页相似图书的内存缓存，由 `app.py` 中的 `similar_books_cache` 维护，先预生成 24 条候选，再按分页参数切片返回。用户评分后，后端会调用算法服务的 `/api/cache/clear` 和 `/api/cache/precompute` 接口，先清除旧缓存，再在后台异步预计算新的推荐结果。

### 4.4 Web后端实现

#### 4.4.1 认证授权与统一响应实现

后端认证由 Spring Security 和 JWT 共同完成。`SecurityConfig` 将系统设置为无状态会话模式，开放 `/users/register`、`/users/login`、`/books/**`、`/themes/**`、Swagger 文档等匿名访问接口，其余接口默认需要认证。`JwtAuthenticationFilter` 会从 `Authorization` 请求头中提取 Bearer Token，校验签名和有效期后，将用户身份写入安全上下文，并把 `userId` 保存到请求属性中，供后续业务层使用。

在接口返回结构上，后端通过 `Result` 和 `PageResult` 对响应进行统一封装。这样做的好处是前端可以只针对 `code`、`message` 和 `data` 三类字段完成统一处理，而不必针对每个控制器编写不同的响应解析逻辑。对于分页查询图书的接口，`PageResult` 还会额外承载当前页、页大小和总记录数。

#### 4.4.2 用户、图书与主题接口实现

用户相关接口由 `UserController` 提供。注册接口在创建用户后立即生成 JWT 并返回给前端，从而实现“注册即登录”的当前流程；登录接口在校验用户名和密码后返回用户对象和 JWT；用户信息更新接口主要支持昵称和年龄的修改，并在后端根据年龄自动回填年龄组。兴趣主题通过 `/users/{userId}/interests` 完成查询和覆盖式保存，兴趣元数据则由 `CategoryController` 提供 `/themes` 和 `/themes/{themeId}` 两个只读接口。

图书相关接口由 `BookController` 和 `BookService` 实现。分页图书列表接口支持按标题或作者关键字搜索，搜索 SQL 定义在 `BookMapper.xml` 中；热门图书接口按 `rating_count > 10` 且平均评分优先的方式排序；最新图书接口按出版年份倒序返回；图书详情接口在查询图书基本信息后，还会补齐中文主题名称。主题名称的填充不是每次都重复查表，而是由 `BookService` 在内存中维护一个简单的主题名称缓存，以减少重复查询开销。

#### 4.4.3 评分、推荐与容错实现

评分功能由 `RatingController` 和 `RatingService` 实现。控制器层先对评分值进行范围和精度校验，要求评分落在 0 至 5 分之间且只能以 0.5 为步长；服务层则在事务中完成“更新已有评分或插入新评分”的逻辑，并在写入后调用 `BookMapper.updateBookRatingStats` 更新图书的平均评分与评分人数。完成数据库写入后，服务层还会触发推荐缓存清理与预计算，但这一过程采用“尽力而为”的策略，不会因为算法服务暂时不可用而回滚用户评分。

推荐接口的后端入口位于 `RecommendationController`，真正的跨服务调用由 `RecommendationService` 完成。当前实现使用 `RestTemplate` 以 JSON 形式向算法服务发送请求，主要调用 `/api/recommend/user-based`、`/api/recommend/similar-items`、`/api/recommend/similar-users`、`/health` 和 `/api/algorithm/info` 等接口。当个性化推荐服务不可用时，后端直接返回错误信息给前端；当图书详情页的相似图书接口调用失败时，`BookController` 会降级为同作者图书列表，以保证详情页仍有可展示的关联结果。

### 4.5 Web前端实现

#### 4.5.1 路由、状态与请求封装

前端入口位于 `src/main.js`，应用启动时注册 Pinia、Vue Router、Element Plus 和图标组件，并初始化 AOS 动画库。路由定义在 `src/router/index.js` 中，核心页面包括首页、登录、注册、资料完善、图书列表、图书详情、个人中心、我的评分和个性化推荐。其中 `/profile`、`/my-ratings` 和 `/recommendations` 三个页面通过路由守卫要求用户登录后访问。

用户登录状态由 `src/stores/user.js` 维护。当前实现会将用户对象和 JWT 同步写入 `localStorage`，页面刷新后可从本地存储恢复登录状态。HTTP 请求统一由 `src/utils/request.js` 封装，所有请求默认指向 `/api`，并在请求拦截器中自动附带 `Authorization` 头；当后端返回 401 或 403 时，前端会统一清除本地登录状态并跳转回登录页。

#### 4.5.2 用户注册、资料完善与个人中心实现

用户注册页面调用 `/users/register` 完成账号创建，后端返回的 `user` 与 `token` 会立即写入 Pinia 和 `localStorage`，随后前端自动跳转到资料完善页面。资料完善流程当前分为两个步骤：第一步填写年龄，并通过 `PUT /users/{userId}` 保存；第二步调用兴趣选择组件，从 `/themes` 获取可选主题后，将选中的 `themeId` 列表提交到 `/users/{userId}/interests`。这样形成了“注册后自动登录 -> 填写年龄 -> 选择兴趣”的实际用户引导流程。

个人中心页面在实现上承担了资料维护而不是认证的职责。页面加载时从本地用户状态恢复用户名、昵称和年龄，再通过兴趣接口拉取当前兴趣列表，并允许用户继续修改昵称、年龄和兴趣主题。前端并没有把所有用户特征都一次性塞进注册表单，而是把影响推荐的核心字段拆成登录后可逐步补全的资料流程，这与系统当前的冷启动设计是一致的。

#### 4.5.3 图书浏览、详情与推荐页面实现

首页 `Home.vue` 负责展示系统概览以及热门图书、最新图书两个入口，这两个区域分别调用 `/books/popular` 和 `/books/latest` 获取固定数量图书。图书列表页 `BookList.vue` 支持关键字搜索、分页切换和网格/列表两种浏览方式，其数据直接来自 `/books` 分页接口。由于搜索逻辑已经由后端封装，前端只需维护当前页、页大小和关键字状态即可。

图书详情页 `BookDetail.vue` 是实现较完整的业务页面之一。页面加载时会同时请求图书详情、当前用户评分、图书评分列表和相似图书列表；用户提交新评分后，前端会延迟重新加载详情页数据，从而让平均评分、评分列表和相似图书结果保持同步更新。相似图书区域使用“换一批”交互，底层依赖 `/books/{bookId}/similar?limit=6&offset=...` 的分页能力。

个性化推荐页 `Recommendations.vue` 在进入页面后会先检查推荐服务健康状态，服务可用时再调用 `/recommendations/user-based` 获取推荐结果。页面允许用户动态调整推荐数量和最低评分阈值，并通过 `offset` 参数实现“换一批”效果。若算法服务不可用，页面会显示显式告警信息，而不是伪造一组与当前实现无关的推荐结果。

### 4.6 系统集成与运行方式

#### 4.6.1 本地启动与配置协同

当前项目最容易复核的运行方式是本地三服务联调。典型启动步骤如下：

```bash
cd book-recommendation-frontend
npm install
npm run dev

cd ../book-recommendation-backend
mvn spring-boot:run

cd ../recommendation-algorithm-service
pip install -r requirements.txt
python app.py
```

在这一路径下，前端通过 `/api` 访问后端，后端再根据 `application.yml` 中的 `recommendation.service.url` 调用算法服务。为了减少本章和实现之间的偏差，本文不再沿用旧稿中大量不可核实的批处理脚本、IDE 初始化截图或固定部署步骤，而是以当前仓库中能够直接运行和核验的本地联调链路为主进行说明。仓库中虽然还提供了 `docker-compose.yml` 作为补充集成文件，但本章实现描述仍以代码与接口最容易逐项对应的本地运行模式为准。

#### 4.6.2 服务调用链路与联调验证

系统的核心联调链路主要有三条。第一条是个性化推荐链路：前端推荐页调用后端 `/recommendations/user-based`，后端再调用算法服务 `/api/recommend/user-based`，算法服务返回分页推荐结果和算法元数据。第二条是图书详情相似推荐链路：前端详情页调用后端 `/books/{bookId}/similar`，后端再转发到算法服务 `/api/recommend/similar-items`，若算法服务失败则由后端降级为同作者推荐。第三条是评分联动链路：前端提交评分到 `/ratings/rate`，后端完成评分写入、图书统计更新，并触发算法服务执行缓存清理与预计算。

从工程实现角度看，这三条链路分别覆盖了本系统的主要交互模式：普通查询、跨服务推荐和评分后的异步联动刷新。也正因为如此，第 4 章不再将“是否使用某个中间件”或“是否提供某个理论上可实现的部署能力”作为实现重点，而是强调在当前仓库代码中已经落地的页面、接口、算法和缓存协作机制。
