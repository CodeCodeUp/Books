# 基于协同过滤与内容特征的图书馆资源智能化推荐系统的设计与实现

---

## 第3章 系统需求分析与设计

### 3.1 需求分析

#### 3.1.1 功能性需求分析

结合当前代码实现，本系统的功能性需求可以归纳为四个核心模块。

**（1）用户管理模块**

用户管理模块负责完成注册、登录、资料完善和个人信息维护。新用户通过用户名和密码注册后，后端直接返回 JWT 令牌，前端保存令牌并进入资料完善流程。资料完善目前采用两步式设计：第一步填写年龄，系统自动计算年龄段；第二步选择阅读兴趣主题，兴趣数据通过 `user_interests` 表保存。用户登录后可以在个人中心修改昵称、年龄和兴趣，并查看个人评分历史。

**（2）图书管理模块**

图书管理模块负责图书浏览、关键词检索、图书详情展示以及热门图书、最新图书和相似图书的获取。系统支持按页展示图书列表，并通过同一个分页接口根据 `keyword` 参数实现标题和作者的模糊搜索。图书详情页除展示图书基础信息外，还需要支持用户评分、查看其他用户评分以及获取相似图书推荐。

**（3）评分管理模块**

评分管理模块负责接收用户对图书的显式评分。当前系统支持 0 至 5 分、0.5 分间隔的评分规则，并通过 `(user_id, book_id)` 唯一约束保证同一用户对同一本图书只有一条有效评分记录。用户重复评分时，系统更新原有评分并刷新图书统计信息。评分模块还提供用户单书评分查询、用户评分历史查询和图书评分列表查询等功能。

**（4）推荐模块**

推荐模块是本系统的核心。推荐页面向登录用户提供个性化推荐，支持设置推荐数量、最低评分阈值以及“换一批”分页切换；图书详情页提供相似图书推荐。推荐结果由后端转发算法服务生成，并随用户评分行为触发缓存清理与预计算。系统还保留健康检查接口，用于在前端判断推荐服务是否可用。

#### 3.1.2 非功能性需求分析

在当前系统中，非功能性需求主要体现在性能、可靠性、安全性和可维护性四个方面。

**（1）性能需求**

系统需要支持数十万级评分数据、数十万本图书和数万用户的日常查询与推荐计算。为满足这一需求，前端采用分页加载，后端将图书浏览与搜索统一为分页接口，算法服务则通过候选预筛选、数据全量初始化后增量更新、推荐结果缓存和异步预计算等方式降低计算开销。当前实现中，用户推荐会预先生成较长推荐列表并按页切分返回，相似图书也使用分页偏移量实现“换一批”。

**（2）可靠性需求**

评分写入属于关键操作，需要保证数据库更新与后续统计刷新的一致性，因此评分服务以事务方式执行。算法服务可用时，系统按正常推荐链路返回结果；若图书详情页的相似图书接口调用算法服务失败，则后端降级为同作者图书推荐；若用户推荐算法在服务内部无法得到有效结果，则算法服务会进一步降级为优质热门图书推荐。评分后触发的缓存清理与预计算属于增强机制，即使调用失败也不应阻塞用户评分流程。

**（3）安全性需求**

系统采用 JWT 作为无状态认证机制，并使用 Spring Security 对接口访问权限进行控制。当前实现中，注册、登录、图书浏览和主题查询属于公开接口，而推荐、评分、个人中心等能力需要登录后访问。用户密码通过 BCrypt 加密后存储，避免明文保存。后端还配置了面向本地开发端口的 CORS 白名单，以支持前后端分离调试。

**（4）可维护性需求**

系统采用前端、后端与算法服务分离的结构，各服务通过 HTTP 接口通信，降低了实现耦合。前端将请求封装在统一的 API 模块中，后端以 Controller、Service、Mapper 分层组织代码，算法服务将数据加载、推荐算法和缓存逻辑拆分为独立模块。数据库结构通过版本脚本维护，便于后续追踪结构变更和功能迭代。

#### 3.1.3 用户角色分析

结合当前业务流程，可以将系统中的用户大致分为三类。

第一类是匿名访问者。这类用户可以浏览首页、图书列表和图书详情，但不能进行评分，也无法访问个性化推荐页。其主要需求是快速了解图书资源和系统功能。

第二类是新注册用户。这类用户已经具备登录身份，但尚未形成足够评分历史。系统通过年龄填写、兴趣选择和热门图书兜底等方式，为其提供初始推荐能力，并引导其尽快通过评分积累个性化数据。

第三类是已形成评分历史的登录用户。这类用户既可能是高活跃用户，也可能只是具备少量评分记录的普通用户。系统会根据其评分数量、兴趣信息和年龄信息选择不同推荐路径，以获得更贴近当前状态的推荐结果。

### 3.2 系统总体设计

#### 3.2.1 系统架构设计

本系统采用前后端分离与算法服务独立部署相结合的架构。整体上可以分为表示层、业务层、算法层和数据层四部分：

```text
Vue 3 前端
    ↓ HTTP
Spring Boot 后端（统一业务接口）
    ↓ HTTP
Flask 算法服务
    ↓
MySQL 数据库
```

前端负责页面交互、状态维护和接口调用；后端负责认证、参数校验、数据读写和算法服务聚合；算法服务负责推荐计算、缓存管理和健康检查；数据库负责存储用户、图书、评分和兴趣等业务数据。该结构的设计目标是将推荐计算与常规业务逻辑分离，便于在不影响 Web 主流程的前提下独立调整算法实现。

#### 3.2.2 模块职责划分

**（1）前端模块**

前端基于 Vue 3、Vue Router、Pinia 和 Element Plus 构建，当前路由包括首页、登录、注册、资料完善、图书列表、图书详情、个人中心、评分历史和推荐页。前端通过统一请求封装处理 JWT 注入、接口错误提示和登录失效跳转，并在推荐页与图书详情页中实现“换一批”、加载状态和交互反馈。

**（2）后端模块**

后端基于 Spring Boot 提供统一业务接口，采用 Controller、Service、Mapper 三层组织结构。当前控制器包括：

- `UserController`：注册、登录、用户信息查询与更新、兴趣读写、用户评分历史。
- `BookController`：图书分页查询、详情、热门图书、最新图书、相似图书和图书评分。
- `RatingController`：评分提交、用户单书评分、用户评分列表和图书评分列表。
- `RecommendationController`：个性化推荐、物品推荐、相似用户、算法信息和健康检查。
- `CategoryController`：图书主题列表与主题详情。

**（3）算法服务模块**

算法服务基于 Flask 构建，主要由 `collaborative_filtering.py`、`item_based_cf.py`、`content_based.py`、`hybrid.py`、`data_loader.py` 和 `cache.py` 组成。它负责用户推荐、相似图书推荐、缓存清理、预计算和健康检查，并在服务启动时完成评分数据、图书数据和内容特征矩阵的初始化。

#### 3.2.4 核心业务链路设计

当前系统中有三条最重要的业务链路。

第一条是注册与资料完善链路：用户注册成功后直接获得 JWT，前端进入资料完善页，依次填写年龄并选择兴趣主题，然后将用户信息和兴趣信息分别提交到后端。

第二条是个性化推荐链路：前端推荐页先调用健康检查接口，再向后端提交 `userId`、`topN`、`offset` 和 `minRating` 参数；后端将请求转发给算法服务；算法服务在缓存命中时直接返回分页结果，缓存未命中时先生成完整推荐列表，再进行切片返回。

第三条是评分刷新链路：用户在图书详情页提交评分后，后端更新 `ratings` 表和图书评分统计，随后调用算法服务的缓存清理与预计算接口，以便用户下次访问推荐页时尽量获得更新后的推荐结果。

### 3.3 数据库设计

#### 3.3.1 核心业务表设计

从当前代码实现出发，系统的核心业务数据主要由五张表支撑：`users`、`books`、`ratings`、`book_theme` 和 `user_interests`。虽然初始脚本中还包含 `favorites`、`recommendations` 等预留表，但它们不是当前主流程的核心依赖，因此本章不作为重点展开。

`users` 表负责保存用户登录身份和基础属性，当前业务中主要使用 `user_id`、`username`、`password`、`nickname`、`age`、`age_group`、`status` 等字段。实体中虽然保留了 `email`、`location`、`country` 等字段，但当前前端资料完善和个人中心的主要可编辑信息是昵称、年龄和兴趣。

`books` 表负责保存图书元数据及推荐所需统计信息，关键字段包括 `book_id`、`title`、`author`、`publisher`、`year`、`theme_id`、`avg_rating` 和 `rating_count`。其中 `theme_id` 用于兴趣主题推荐与内容相似候选筛选，`avg_rating` 和 `rating_count` 同时用于图书排序、热门图书筛选和质量兜底。

`ratings` 表负责记录用户对图书的显式评分，是协同过滤和离线评估的核心数据来源。关键字段包括 `rating_id`、`user_id`、`book_id`、`rating`、`rating_date` 和 `created_at`。

#### 3.3.2 主题与兴趣关系设计

为了支撑兴趣选择和基于主题的推荐，系统逻辑上使用 `book_theme` 与 `user_interests` 两张表。

`book_theme` 表保存主题主数据，如主题英文名、中文名和描述，用于前端展示主题列表和将图书的 `theme_id` 映射为可读名称。后端在查询图书时会通过 `theme_id` 查找主题名称，并填充到实体的非数据库字段 `themeName` 中。

`user_interests` 表用于建立用户与主题之间的多对多关系。用户在资料完善页或个人中心中选择的主题，会以 `(user_id, theme_id)` 组合形式写入该表。算法服务随后根据这些主题信息完成兴趣推荐和兴趣加权。

从关系上看，系统的核心逻辑可以表示为：

- `users` 与 `ratings` 是一对多关系。
- `books` 与 `ratings` 是一对多关系。
- `books` 与 `book_theme` 是多对一关系。
- `users` 与 `book_theme` 通过 `user_interests` 建立多对多关系。

#### 3.3.3 索引与约束设计

当前数据库设计中的关键约束与索引如下。

第一，`users.username` 具有唯一约束，用于保证登录名唯一。

第二，`ratings` 表上的 `(user_id, book_id)` 联合唯一约束用于保证同一用户对同一本图书只有一条评分记录，这也是后端实现“重复评分则更新”的基础。该表同时包含 `user_id`、`book_id`、`rating` 和 `rating_date` 索引，以支持评分查询、评分统计和协同过滤数据提取。

第三，`user_interests` 表上的 `(user_id, theme_id)` 联合唯一约束用于防止同一兴趣被重复保存，`user_id` 与 `theme_id` 的普通索引则支持兴趣读取和主题反向查询。

第四，`books` 表在 `author`、`year`、`avg_rating` 等字段上建立索引，用于支撑图书排序和候选筛选；同时保留了标题和作者的全文索引。需要说明的是，当前后端搜索实现主要通过 `title` 和 `author` 的 `LIKE` 查询完成，全文索引更多体现为数据库层的预留优化条件，而不是当前代码中的主搜索路径。

### 3.4 推荐算法设计

推荐算法设计的目标，不只是“给出推荐结果”，而是要在当前系统数据条件下形成一条可落地、可解释且可扩展的推荐链路。结合现有代码实现，本文在算法设计上遵循以下三个原则：第一，优先复用真实可获取的数据，即评分历史、年龄和兴趣主题，不引入系统中无法稳定采集的特征；第二，优先按用户状态和图书状态进行路由，而不是为所有场景强行套用统一策略；第三，在保证推荐质量的同时考虑工程成本，使算法能够通过接口稳定服务于推荐页和图书详情页。

#### 3.4.1 推荐页算法路由设计

推荐页算法设计的核心任务，是根据用户当前数据完整度为其选择合适的推荐路径。当前实现中，算法服务入口方法接收 `user_id`、`top_n` 和 `min_rating` 等参数，输出为包含图书基础信息、推荐理由和部分算法元数据的推荐列表。设计上先做状态判断，再决定是否进入协同过滤、内容推荐或动态混合流程。

推荐页采用基于用户状态的路由策略。算法服务首先判断用户是否有评分历史、是否选择兴趣以及是否填写年龄，然后从下表所示策略中选择对应路径。

| 用户状态 | 实际策略 | 说明 |
|:---|:---|:---|
| 有评分 + 有兴趣 | 三层混合推荐 | 用户协同过滤 + TF-IDF + 兴趣加权 |
| 有评分 + 有年龄但无兴趣 | 双层混合推荐 | 用户协同过滤 + TF-IDF |
| 有评分 + 无年龄且无兴趣 | 双层混合推荐 | 用户协同过滤 + TF-IDF |
| 无评分 + 有兴趣 | 兴趣主题推荐 | 按 `theme_id` 匹配图书主题 |
| 无评分 + 有年龄 | 年龄偏好推荐 | 年龄辅助排序 |
| 无评分 + 无兴趣且无年龄 | 优质热门图书 | 评分与评价人数兜底 |

该路由设计可以概括为以下流程：

1. 读取目标用户评分记录，判断是否存在历史行为。
2. 读取用户基础特征，判断是否存在年龄或兴趣信息。
3. 若同时存在评分历史与兴趣，则进入三层混合推荐。
4. 若存在评分历史但没有兴趣，则进入双层混合推荐。
5. 若不存在评分历史，则根据兴趣、年龄和兜底规则进入冷启动路径。

这一设计说明当前系统的推荐页不是简单的“协同过滤与内容推荐固定权重混合”，而是先进行状态路由，再在部分路径中进行动态比例混合。这样做的好处在于，每类用户都能使用更符合其数据条件的算法，避免新用户被强行送入协同过滤，也避免高活跃用户仅收到规则式推荐。

#### 3.4.2 协同过滤设计

协同过滤部分承担“从行为中学习偏好模式”的职责，分为推荐页使用的用户协同过滤和图书详情页使用的物品协同过滤两类。

在推荐页中，用户协同过滤的设计目标是为目标用户寻找行为相近的用户群体，并从这些用户的高分图书中生成候选推荐。当前实现要求目标用户与候选用户至少存在 2 本共同评分图书，然后对共同评分向量计算余弦相似度，并保留相似度较高的前若干个用户作为邻居集合。随后，系统从这些邻居的高分图书中收集候选图书，并通过加权平均预测目标用户的潜在评分：

\[
\hat{r}_{u,i}=\frac{\sum_{v \in N(u)} sim(u,v)\cdot r_{v,i}}{\sum_{v \in N(u)} sim(u,v)}
\]

其中，\(N(u)\) 表示目标用户的相似用户集合。该设计的关键不在于对全量用户做穷举计算，而在于先通过共同评分图书筛选候选邻居，再对邻居集合中的高分图书做预测评分。这使推荐页的协同过滤同时具备可计算性和个性化深度。

用户协同过滤在实现上的主要步骤可以归纳为：

1. 获取目标用户评分记录与已评分图书集合。
2. 在评分数据中筛选也评分过这些图书的其他用户。
3. 对共同评分图书不少于 2 本的用户计算余弦相似度。
4. 选取相似度较高的用户作为邻居集合。
5. 从邻居高分图书中收集候选图书。
6. 对候选图书计算预测评分并按分数排序返回。

在图书详情页中，物品协同过滤负责生成相似图书。其设计目标不是预测用户分数，而是回答“与当前图书最相近的图书有哪些”。当前实现流程为：先找到评分过目标图书的用户，再以这些用户评分过的其他图书作为候选集，最后基于共同评分用户的向量计算图书相似度。由于候选图书集合远小于全库图书，这一设计能够显著降低计算量，并使相似图书结果更容易解释。

#### 3.4.3 内容推荐与冷启动设计

内容推荐部分承担“在行为数据不足时仍然给出合理结果”的职责，也是当前系统解决冷启动问题的主要手段。它包含“基于评分历史的 TF-IDF 内容推荐”和“基于兴趣与年龄的冷启动设计”两个部分。

第一部分是 TF-IDF 内容推荐。系统将标题、作者和出版社拼接为组合文本，提取 1000 维 TF-IDF 特征，并与年份和平均评分标准化特征拼接，用于生成图书内容向量。对于有评分历史的用户，系统再以用户已评分图书向量为基础，按照评分高低构建加权用户画像，并通过余弦相似度找出与该画像最接近的候选图书。该设计的本质是：把用户过去喜欢的图书内容，转化为可计算的文本特征表达。

这一部分的设计流程可概括为：

1. 提取图书的组合文本并构建 TF-IDF 特征矩阵。
2. 将年份和平均评分作为辅助数值特征与文本特征拼接。
3. 对目标用户已评分图书按评分高低加权求和，得到用户内容画像。
4. 排除用户已评分图书，并对候选图书增加最低评分人数约束。
5. 计算画像与候选图书向量的余弦相似度，返回相似度最高的结果。

第二部分是面向冷启动的兴趣与年龄策略。当用户没有评分历史时，系统优先检查其是否选择了兴趣主题。若存在兴趣主题，则根据 `theme_id` 匹配对应图书，并结合年龄偏好做辅助排序；若没有兴趣但填写了年龄，则使用年龄偏好与图书质量分数构造排序分；若两类特征都不存在，则返回优质热门图书作为兜底推荐。

该冷启动设计采用“兴趣优先、年龄辅助、质量兜底”的原因在于：兴趣是用户主动表达的偏好，信号强度最高；年龄能够在缺少兴趣时提供一定排序依据；热门优质图书则保证系统在极端缺信息情况下仍有稳定输出。

图书详情页的内容相似推荐也使用同一套内容能力。系统优先通过 TF-IDF 向量与候选预筛选生成内容相似图书；若相关向量不可用，则退回到作者、主题、出版社、年份和评分差异构成的属性匹配方法。这一回退设计保证了内容相似推荐不会因单一特征失败而完全失效。

#### 3.4.4 动态混合与缓存刷新设计

混合设计的目标，是在“协同过滤的个性化深度”和“内容推荐的冷启动能力”之间建立可自适应的平衡。当前系统没有直接采用固定权重，而是根据用户侧和图书侧的数据质量动态计算混合比例。

（1）推荐页，用户侧动态混合

在推荐页中，系统根据当前用户的相似用户数量与平均相似度构造协同过滤置信度，并据此计算协同过滤占比。其 LaTeX 表达式为：

\[
confidence_{user}=\min\left(\frac{N_{similar}}{50},1\right)\times sim_{avg}
\]

\[
ratio_{cf}^{user}=0.50+0.40\times confidence_{user}
\]

\[
ratio_{content}^{user}=1-ratio_{cf}^{user}
\]

其中，\(N_{similar}\) 表示相似用户数量，\(sim_{avg}\) 表示平均相似度。根据该映射关系，协同过滤占比范围为 50\% 至 90\%，内容推荐占比范围为 10\% 至 50\%。当相似用户数量更多、平均相似度更高时，说明当前用户行为数据更可靠，系统会提高协同过滤权重；反之，则由内容推荐承担更多比例。若用户选择了兴趣主题，系统会在动态混合结果上对主题匹配的候选图书执行兴趣加权，从而使显式偏好得到优先体现。

从策略分支看，推荐页根据用户数据丰富程度采用不同路径：当用户既有评分历史又有兴趣主题时，采用“协同过滤 + TF-IDF 内容推荐”的动态混合，并对兴趣匹配图书进行加权；当用户有评分历史但无兴趣主题时，采用不带兴趣加权的动态混合；当用户无评分但具有年龄或兴趣等基础特征时，进入“兴趣优先、年龄辅助、质量兜底”的冷启动推荐；当用户既无评分又无基础特征时，则降级为高质量热门图书推荐。

（2）详情页，物品侧动态混合

图书详情页的设计思路与推荐页类似，但强调的是目标图书的数据质量，而不是用户数据质量。只有当物品协同过滤结果和内容相似结果同时存在时，系统才会计算物品侧置信度并执行动态混合。其 LaTeX 表达式为：

\[
score_{qty}=\min\left(\frac{N_{rating}}{100},1\right)
\]

\[
score_{quality}=\min\left(\frac{N_{cf}}{20},1\right)\times sim_{cf}^{avg}
\]

\[
confidence_{item}=score_{qty}\times score_{quality}
\]

\[
ratio_{cf}^{item}=0.40+0.45\times confidence_{item}
\]

\[
ratio_{content}^{item}=1-ratio_{cf}^{item}
\]

其中，\(N_{rating}\) 表示目标图书的评分数量，\(N_{cf}\) 表示物品协同过滤得到的候选图书数量，\(sim_{cf}^{avg}\) 表示物品协同过滤候选的平均相似度。按照当前实现，图书详情页中协同过滤占比范围约为 40\% 至 85\%，内容特征占比范围约为 15\% 至 60\%。因此，热门且协同过滤候选质量较高的图书会更偏向物品协同过滤，而冷门图书则更多依赖内容特征。若目标图书不在算法服务已加载的图书数据中，系统使用 50\% : 50\% 的默认比例；若只有单路结果可用，则直接退化为纯物品协同过滤或纯内容推荐；若两路结果都不可用，则继续降级为同作者图书推荐。

（3）缓存与降级

缓存与刷新设计服务于算法的工程可用性。用户推荐接口在算法服务中一次性生成较多候选结果，并以文件形式缓存完整推荐列表，随后按 `offset` 分页返回；图书详情页的相似图书结果则采用算法服务内存缓存，先预生成较完整的候选集合，再按分页参数切片返回。用户提交新评分后，后端在更新图书评分统计信息的基础上，依次调用算法服务的 `/api/cache/clear` 与 `/api/cache/precompute` 接口，先清除该用户旧缓存，再异步触发新的推荐预计算，以缩短最新评分影响推荐结果的延迟。

容错方面，推荐页在算法服务整体不可用时不会直接伪造降级推荐，而是由后端向前端返回推荐服务不可用的错误信息；图书详情页在后端调用算法服务失败时，会降级为同作者图书列表。在算法服务内部，若物品协同过滤和内容特征两路结果均为空，也会先执行同作者降级策略，从而保证详情页始终具备基本可返回结果。
